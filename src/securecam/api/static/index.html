Video goes straight from the camera to this browser over WebRTC. The Raspberry Pi does not re-encode anything, so watching live costs it almost nothing.

How notifications work

When motion turns into an event, the Raspberry Pi itself sends you a push message with a snapshot attached. It does not go through any SecureCam server, and it keeps working while nobody has this page open.

All of it is configured in two files on the Pi, over SSH. There is deliberately no settings screen for it: a stolen browser session must never be able to redirect or silence your alarms.

/etc/securecam/config.yamlWhich provider, how loud, who receives it.
/etc/securecam/securecam.envSecrets only: API tokens. Readable by root alone.

Which provider should I pick?

ntfy Free, no account, no sign-up at all. Good enough for almost everyone. Start here.
Pushover One-off payment per platform. Its emergency priority keeps re-alerting until you acknowledge it on the phone, which ntfy cannot do.

Things worth knowing

  • A failed notification is retried for 24 hours, so a short internet or Wi-Fi outage never loses an alert.
  • The recording never waits for the notification. Clips are saved even when your phone is unreachable.
  • While the camera is disarmed, no notifications are sent at all.
  • only_if_person: true holds back alerts unless the AI saw a person. It needs ai.enabled, and it fails open: if the AI is unreachable you still get the alert.

Set up ntfy (free)

What is a "topic"?

ntfy has no accounts and no registration. A topic is just a name you invent — a word in a URL. Your Pi publishes to https://ntfy.sh/<your-topic> and your phone listens on the same name. That is the entire system.

You do not create it anywhere first. The moment something publishes to a name, that topic exists. This also means the name is the password: anyone who guesses it can read your alerts and send you fake ones. So do not use home or frontdoor. Use something long and random, for example: 

securecam-k7q2fp9wzx4m

Make up your own on the Pi if you like:

echo "securecam-$(head -c 8 /dev/urandom | base32 | tr 'A-Z' 'a-z' | tr -d '=')"

Write that name down. You will type the exact same string in two places.

1. Subscribe on your phone

  1. Install ntfy from the Play Store or the App Store.
  2. Open it and tap the + button.
  3. Type your topic name exactly as you chose it. Leave the server on ntfy.sh.
  4. Tap Subscribe. It now appears in the list, empty.

Check it works before touching the Pi — from any browser, open https://ntfy.sh/<your-topic> and send a test message. It should appear on your phone within a second.

2. Make it loud

By default Android and iOS treat it as an ordinary notification. In the ntfy app, open your topic, tap the ⋮ menu, and set a dedicated sound and Override Do Not Disturb for that topic. Without this step a night-time alarm will not wake you.

3. Tell the Pi about it

sudo nano /etc/securecam/config.yaml

The topic goes in recipients[].target — not in the ntfy: block. That block only holds settings shared by every recipient. 

notifications:
  enabled: true
  provider: ntfy
  alarm: true
  include_snapshot: true
  only_if_person: false
  cooldown_seconds: 0
  ntfy:
    server: https://ntfy.sh
    priority: 5
    tags: ["rotating_light"]
  recipients:
    - id: my-phone
      enabled: true
      target: securecam-k7q2fp9wzx4m

Add a second phone by adding another entry under recipients with its own id and its own topic. Each gets its own copy of the alert.

Public ntfy.sh topics need no token, so securecam.env stays untouched. Only if you run your own ntfy server with access control do you add SECURECAM_NTFY_TOKEN=tk_... there.

4. Apply and test

sudo securecam-admin check-config
sudo systemctl restart securecam
sudo securecam-admin test-notify

Your phone should buzz. If it does not, see Nothing arrives? in the sidebar.

Set up Pushover (paid)

Pushover costs a one-off fee per platform. You get it for the emergency priority: the alert repeats every 30 seconds for 10 minutes until you acknowledge it on the phone, and it ignores the phone's quiet hours.

1. Create the account and the app

  1. Sign up at pushover.net and install the Pushover app on your phone.
  2. On the website's front page you will see your user key — a 30-character string. That is your target.
  3. Scroll down and click Create an Application/API Token. Name it "SecureCam". The token it gives you is the secret.

So Pushover has two different strings and they are not interchangeable: the user key says who to notify and lives in config.yaml; the application token says who is allowed to notify and lives in securecam.env.

2. Store the token

sudo nano /etc/securecam/securecam.env
SECURECAM_PUSHOVER_TOKEN=azGDORePK8gMaC0QOYAMyEEuzJnyUi
sudo chmod 600 /etc/securecam/securecam.env

3. Configure it

sudo nano /etc/securecam/config.yaml
notifications:
  enabled: true
  provider: pushover
  alarm: true
  include_snapshot: true
  pushover:
    priority: 2
    retry_seconds: 30
    expire_seconds: 600
    sound: persistent
  recipients:
    - id: my-phone
      enabled: true
      target: uQiRzpo4DXghDmr9QzzfQu27cmVRsG

priority: 2 is the emergency mode. Use 1 if you would rather not be nagged until you tap the notification.

4. Apply and test

sudo securecam-admin check-config
sudo systemctl restart securecam
sudo securecam-admin test-notify

Connect it to an AI

The AI looks at a snapshot from each event and answers one question: was that a person? The answer is stored with the event, so you can filter the Events tab by it and hold back notifications for cats, branches and passing headlights.

This is entirely optional. Everything else works without it.

1. Get an API key

The built-in provider is openai_vision. It works with the OpenAI API and with any service that speaks the same protocol, including ones you host yourself. Create a key at your provider and copy it.

If your detection service has its own protocol, use the generic_http provider instead and map the response fields in config.yaml.

2. Store the key

Keys never go in config.yaml, only in the environment file:

sudo nano /etc/securecam/securecam.env
SECURECAM_AI_API_KEY=sk-...
sudo chmod 600 /etc/securecam/securecam.env

3. Turn it on

sudo nano /etc/securecam/config.yaml
ai:
  enabled: true
  provider: openai_vision
  snapshot_count: 1
  min_confidence: 0.6
  recheck_interval_seconds: 60
  max_checks: 4
  openai_vision:
    base_url: https://api.openai.com/v1
    model: gpt-4o-mini
    api_key_env: SECURECAM_AI_API_KEY
    detail: low
    max_tokens: 200

Point it at a different service by changing base_url and model. min_confidence is the cut-off below which a "person" answer is treated as no person; raise it if you get false positives.

Two frames is not the same as two looks

These two settings sound alike and do very different things.

snapshot_count How many frames go into one request. They are taken snapshot_interval_seconds apart and sent together, so the model sees a short burst instead of a single instant. It widens the moment, nothing more.
recheck_interval_seconds How long to wait before looking again, later in the same event. Set to 0 to switch re-checking off.

Re-checks exist because the first second of an event is often the least interesting one. You drive up, the sensor fires, the camera sees a car and the AI correctly says "no person" — and then you get out. With the defaults SecureCam notices the sensor is still active, takes a fresh snapshot a minute later and asks again. It keeps doing that until it finds a person, the motion stops, or it has asked max_checks times. All four checks empty and the event is labelled false positive in the Events tab.

If a later check does find a person, the notification you would otherwise never have received is sent right then, even when only_if_person had already suppressed it.

4. Apply and test

sudo securecam-admin check-config
sudo systemctl restart securecam
sudo securecam-admin test-ai

Keeping the bill small

  • detail: low with snapshot_count: 1 keeps each event to a fraction of a cent.
  • An event costs at most max_checks calls, and only ever more than one if the sensor keeps seeing movement.
  • Lower max_checks to 1 to get the old behaviour: one look at the start and nothing after.
  • Disarming the camera stops recording and every AI call, so a disarmed camera costs nothing.
  • Recording never depends on the AI. A wrong key or a provider outage still leaves you the clip, and the analysis is retried for 24 hours.
  • Set notifications.only_if_person: true once you trust the results. That cuts false alarms, not cost.

Nothing arrives?

Work down this list. Each command tells you what failed and what to do about it.

1. Ask the camera

sudo securecam-admin diagnose

This prints every subsystem, whether it is healthy, and the exact next command when it is not. The Status tab shows the same information.

2. Check the config actually parsed

sudo securecam-admin check-config

A recipient left at CHANGE-ME, or enabled: false on the recipient rather than the block, is rejected here with the line to fix.

3. Send a test on demand

sudo securecam-admin test-notify

This ignores motion entirely and goes straight to the provider, so it isolates the delivery step.

4. Read the log

sudo journalctl -u securecam -n 100 --no-pager

Common causes

  • Topic mismatch. The name in config.yaml and the one in the phone app must match exactly, including case and dashes.
  • Silent by design. The alert arrived but the phone did not make a sound. Give the topic its own sound and let it override Do Not Disturb.
  • Camera disarmed. Check the badge in the header. Disarmed means no events, so no notifications.
  • only_if_person with no AI. If ai.enabled is false while only_if_person is true, nothing qualifies.
  • Battery optimisation. Android may kill the ntfy app in the background. Exclude it from battery optimisation.
  • Config not reloaded. Changes need sudo systemctl restart securecam.
